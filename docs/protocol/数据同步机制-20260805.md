# 平台数据同步机制与丢帧检测

> 结论截至:2026-08-05(基于 2026-08-05 两起事故排查 + 官方前端 assets-release.js 逆向)
> 配套阅读:`docs/GLOSSARY.md`(协议号)、`docs/ARCHITECTURE.md`(架构)、`docs/INCIDENTS.md`(事故库)

## 一、数据推送通道

采集端用 **301 多台订阅**一条连接收全平台桌台帧:

| 协议 | 帧 | 内容 | 用途 |
|---|---|---|---|
| 301 | 快照 | 全量桌台 `gameTableMap`(含 `roadPaper` 全量路纸) | 快照校准 |
| 104 | 新局 | roundId/roundNo/倒计时 | 时钟对齐 |
| 106 | 发牌 | 逐张开牌 | 落盘 |
| **107** | 结算 | roundId + bootReport(totalCount) + cardResult/winPoints | **主数据源,自建路纸** |
| **161** | 单桌路纸 | SINGLE_ROAD: `{tableId, roundId, roadPaper}` | 增量校准 + 跳号检测 |
| 160 | 桌状态 | betFlag | 判活 |
| 103 | 新靴 | `newBootNo`(靴标识) | 路纸清零 |

## 二、丢帧检测信号

### 可用的检测信号

| 信号 | 来源 | 特性 | 是否可用 |
|---|---|---|---|
| `bootReport.totalCount` | 107 | 靴内局序号,基本逐局 +1 | ✅ 跳号(46→49)可检测 |
| `161 version` | 161 | 与 totalCount 同源 | ✅ 同跳 |
| `roundId` | 104/107/161 | 每局唯一,**但间隔 200+,非 +1** | ❌ 不能直接判丢 |
| `newBootNo` | 103 | **靴标识,非局号**,每靴一个 | ❌ 不能判丢局 |
| `roundNo` | 104 | 字符串(GB1226804013) | ❌ 非数字序号 |

**结论:推送数据中无"逐局 +1 的靴号"字段**。唯一可靠的丢局信号是 **totalCount / 161 version 跳号**。

### 跳号检测的局限(实测)

实测某桌 1022 帧检测到 **160 次跳号**——跳号极频繁,分两类:
1. **服务器常态跳号**:官方客户端也这么收,不代表采集端丢帧
2. **整桌断流**:104 和 107 的 roundId 序列同时缺段(丢约 10 局)

**区分方法**:交叉比对 104(新局)与 107(结算)roundId 是否对齐。都丢 → 整桌断流;仅 107 丢 → 单帧丢失。

## 三、官方客户端机制(逆向 assets-release.js)

### 1. 没有定时拉路纸

官方定时器仅有:
- **心跳 1s**:`setInterval(sendHeartbeat, 1000)` —— 保活 + **请求超时检测**
- TAG302 场景 10s(拉 RoadBetList)

**路纸不靠定时拉**,靠服务器推 + 事件触发补拉。

### 2. 重新拉取的触发条件(dataUpdateTask)

官方有 **6 种补拉任务**,`ai.roadPaper=1` 触发条件:

| 触发 | 逻辑 |
|---|---|
| 161 增量解析失败 | `parseRound(t)` 返回 false → `addTask(roadPaper, tableId)` |
| 版本不一致 | 桌有 `roadPaperVersion` 但 `roadPaper` 缺失/不匹配 → 拉 |
| 进新桌 | 收到桌数据但无 roadPaper 且无 version → 拉 |
| bootReport 缺失 | 有 roundId 但无 `bootReportVersion` → 拉 |
| 下注限制/靴号版本不一致 | version 对不上 → 对应任务 |

**执行**:`callFunc` 每轮最多 10 桌,`sendGetTableListRoad(tableIds)` 发 `TABLE_ROAD` 主动拉,响应后 `serverRecv()` 清队列继续。

**关键**:官方是**每次收到桌数据都校验版本,版本对不上立即补拉**;被动检测是采集端的兜底。

### 3. "网页刷新"提示的触发

从心跳逻辑(`sendHeartbeat`):

```js
if (a - this._msgQueue[0].timestamp > this._msgTimeout) {
  o5.instance().reConnection("(协议超时)|msgId:...");
  this.reconnect();                          // 重连
  uo.instance().sendNotify(ua.SOCKET_REQ_TIMEOUT, a);  // 通知超时
}
```

触发条件:
- **协议请求超时**:心跳 1s 检测,某请求超 `_msgTimeout` 未响应 → 重连
- **断线重连**(SOCKET_CONNECT):`isReConnection=!0`
- **重连反复失败**:`reconnect()` 多次失败 → 前端提示刷新页面

## 四、对采集端的启示

官方"版本校验 + 主动补拉"思路值得借鉴:
1. **每次 107 到达时校验**:不仅更新 totalCount,还检查跳号 → 立即补拉
2. **整桌断流检测**:某桌 104/107 长时间无 roundId 推进 → 标记疑似断流,周期性补拉
3. **主动巡检**:对活跃桌定期发 `TABLE_ROAD`(10053)对比路纸,替代纯被动检测
