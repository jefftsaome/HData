## 人数口径说明（2026-07-20 补充）

110 押注快照帧的 `jackpotPoolInfos` 按下注点拆分，常见 betPointId：
- 3001 庄 / 3013 庄免佣 / 3002 闲 / 3003 和；4113、4114、5819、5820 等为侧注池。
- 3003（和池）只在当局有人买和时才出现在帧里，缺席即和池为 0（约半数帧含 3003）。
- 每帧另有 `currentRoundPlayerCount`（当局总下注人数）与 `currentRoundPlayerAmountCount`（当局总下注额）。

**在线人数（online_number）与下注人数是两种口径，不能直接互比：**
- 在线人数来自大厅 10052 周期扫描快照，可能滞后一个扫描周期（实测可达 40 秒+）；
- 分池人数（b_cnt/p_cnt/t_cnt）是当局累计下注人次，一人买多个池会被重复计数；
- 因此会出现"在线 163 < 闲人数 288"这类表面异常（实测局 476700425：在线快照取自 40 秒前的 163，结算后 1 秒大厅刷新为 412，当局下注人数 368）。
- 分析"当局热度"应优先使用 `currentRoundPlayerCount`；在线人数只宜作趋势参考。

## 推送节奏（2026-07-21 实测）

110 押注快照帧的推送为"2 秒基准节拍 + 变动时加密"，非严格等间隔。
基于最近 24 小时 138,708 个局内相邻帧间隔：

- 中位数 2002ms，均值 1881ms，p25~p75 = 2001~2003ms，p99 = 4005ms；
- 1.5~2.5s 占 76.7%（标准节奏）；0.5~1.5s 占 20.5%（开局/封盘前资金剧烈变动时加密）；4s 以上约 2.8%（平静期）。

分析含义：
1. 帧数值连几帧不变 = 该时段无人下注（有变化才推）；
2. 封盘前帧最密（可达 1 秒级），"最后一跳"检测精度在关键时刻最高；
3. 帧间隔本身可作为衍生指标：突然加密 = 桌面资金剧烈变化。

### WS 连接 URL 解剖（真实客户端）

```
wss://wsproxy.{backendDomainUrl}/
  ?playerId=105452510
  &jwtToken={game_token}
  &deviceId=1784893260093339843-95557669-55953617   ← 三段式！
  &platformId=1&applicationId=5&version=v1.0.5       ← 静态尾参（未轮换）
```

**deviceId 三段格式**：`{fixedDeviceId}-{每连接随机8位}`。
fixedDeviceId（前两段）由 egret 客户端首次运行生成并持久化在
游戏源站 localStorage（键 `fixedDeviceId`）；第三段每次连接随机生成。
hdata 旧版只用两段，2026-07-24 实测两段/三段均被拒过，真正死因见下。

### 10026 拒登排查结论（2026-07-24，逐项实测排除）

| 怀疑点 | 实测结果 |
|:--|:--|
| 域名/证书失效 | 已修（ignore_https_errors），非因 |
| WS URL 静态尾参轮换 | 未轮换，与 hdata 常量逐字一致 |
| deviceId 格式 | 对齐真实客户端三段式后仍拒，非因 |
| token 绑定登录 IP | **属实**：浏览器走 Clash 代理（出口 219.76.134.210），本机直连被墙/不同出口；探针挂同一代理后仍拒，非唯一因 |
| protocolCodecConfig 空表 | 补齐 6 哈希后仍拒，非唯一因 |
| **token 一次性（jti 单次消费）** | **最终结论**：params 派生的 game_token 只在"第一条连接"上有效；浏览器客户端断开后，任何同 jti 重连（包括真实客户端自己）都被 10026。每次页面加载平台都发新 token，不存在"同 jti 重连"场景 |

**推论**：复用浏览器会话 token 的路不可行。可持续方案只有两条：
1. 修复 HTTP 打码登录（当前病根：`SignError`，平台 7 月下旬更换了
   接口签名算法/密钥，打码本身能过、签名不被接受）；
2. 浏览器登录时**拦截 egret iframe 请求**（拿到 params 后立刻 abort，
   不让真实客户端消费 token），token 留给采集程序自用。

### 修复落地（2026-07-24 晚，全部实测通过）

1. **HTTP 打码登录已修复**：`SignError` 真凶为签名脚本未打进 wheel
   （详见 docs/login-api-capture-20260717.md"运维记录：2026-07-24"），
   非平台更换签名算法——wasm 文件与站点逐字节一致，重试加固到 6 次。
2. **protocolCodecConfig 六哈希已固化**：`codec.PROTOCOL_CODEC_CONFIG`
   常量（值同上表），`build_login_msg` 不再发空表。
3. **deviceId 三段式已对齐**：`session.generate_device_id()` 生成完整三段，
   `ensure_device_id_suffix()` 给两段 fixedDeviceId 追加每连接随机第三段；
   `build_ws_config` 与 `leyu_ws` 备用域名构造均已接入。
4. **端到端冒烟通过**（`HDATA_PROXY=http://127.0.0.1:7890 uv run python
   scripts/client_e2e_smoke.py`）：HTTP 打码登录 → WS 登录（六哈希+三段
   deviceId）→ 大厅 37 桌 → 进桌（经典百家乐B08，dealer=Kalia）→
   正常收 road/bet 推送事件。同 jti 重连限制仍然存在：每次 WS 连接前
   必须用 `client.login()` 刷新出新鲜 game_token。
5. **jti 消费追踪机制**（2026-07-24 深夜）：`_refresh_cb` 的"60s 新鲜
   跳过"曾只看时间窗——缓存命中场景 login → get_tables → enter_table
   一气呵成（全程 <60s）时，enter_table 复用被 get_tables 消费过的死
   token，必现 10026。修复：session 增加 `_token_consumed` 标记
   （WS 登录成功置位、刷新成功复位），跳过前提追加"未被消费"。
   实测连续进 3 张桌无 10026；刷新限流真实存在（实测触发一次
   TokenRefreshError），退避重试机制自动扛住。
6. **"龙争虎斗"桌名之谜定案**：大厅按 gameTypeId=2001 过滤"经典百家乐"
   会带出桌名"龙争虎斗 01~10"的桌，401 快照自证 gameTypeName 就是
   "经典百家乐"（越南厅）——它是经典百家乐分类下的主题桌名系列，
   并非龙虎斗游戏（真龙虎桌 gameTypeId=2006，桌名"龙虎E25"式）。
   **桌名 ≠ 游戏类型**；物理桌台系列看 physicsTableNo 字母前缀
   （J=龙争虎斗系、H/C/B=经典百家乐系、U=极速系、E=龙虎/边游戏系）。
   龙争虎斗桌号轮班变动（同晚实测 01/03/04/05/08/09/10 均出现过）。

- `tableOnline` 只含两个键：`onlineNumber`、`totalAmount`（121/121 桌帧一致）。

  不是我们解析或取值路径的 bug。** 大厅总下注额指标不可用，分析热度只能
