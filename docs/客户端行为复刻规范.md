# 游戏客户端行为复刻规范

> 目标：**一比一复刻官方游戏客户端的网络行为**，使采集侧与真实玩家
> 浏览器在平台眼中不可区分，并为后续"用历史数据复现历史牌局"提供
> 客户端行为基准。
>
> 本文只收"客户端怎么做事"（生命周期/心跳/重连/指纹/节奏），
> 协议报文目录见 `leyu-protocol-complete.md`，接入实现见
> `平台接入机制.md`。每条结论标注证据等级：
> ✅ 实测确认 / 📦 逆向官方客户端确认 / ⚠️ 推断待验证。

## 1. 连接分层模型

官方客户端（浏览器）一局游戏的完整链路分四层，每层生命周期独立：

| 层 | 内容 | 失效表现 | 恢复代价 |
|---|---|---|---|
| L0 入口 | leyu.me → code.js/mappings → 主站域名 | 域名被墙/更换 | 重新发现（廉价） |
| L1 站点会话 | HTTP 登录 → site token | token 过期/被踢 | 完整重登（贵，打码） |
| L2 游戏会话 | venue/launch → 游戏 JWT + backendDomainUrl | JWT 过期、会话被作废 | venue/launch 刷新（廉价） |
| L3 WS 长连接 | 连 backendDomainUrl，WS 登录（jti 单次消费） | 断连 | 重建连接（需有效 L2） |

**关键事实**：L3 断开时，平台侧的游戏会话上下文（你已占用的桌台、
订阅槽位）**不保证保留**。浏览器端的表现是：断线重连后客户端会
重新走一遍 venue/launch + 重新进桌，用户感知是"卡了一下"。
（✅ 实测：我方重连后 venue/launch 偶发 `no_params_in_url`，
即平台会话冷却期的直接证据。）

## 2. 心跳机制（2026-08-01 事故后重点澄清）

### 2.1 官方客户端怎么做

- **应用层心跳**：WS 登录后每 **10s** 发协议帧 `pid=3`，
  载荷 `{clientTime, deviceType, deviceId}`。✅/📦
  （逆向官方前端确认，我方已复刻，见 `client.py::_heartbeat_loop`）
- **无心跳惩罚**：服务端约 **40~60s** 未收到心跳主动断连（✅ 实测）。
- **传输层 ping/pong**：浏览器 WebSocket API **不暴露也不主动发送**
  WS 协议级 ping 帧；Chrome 不依赖 WS ping 保活，完全靠应用层心跳。
  📦（WebSocket API 规范 + Chrome 行为，待官方 JS 二次确认 ⚠️）

### 2.2 我方当前实现的偏差（待修）

python-websockets 库**默认开启**传输层 ping（`ping_interval=20s`，
`ping_timeout=20s`），我方 `connect()` 未显式关闭。后果：

1. **指纹差异**：官方客户端不发 WS ping 帧，我们每条连接每 20s
   多发一对 ping/pong——一个多余的可探测特征。📦
2. **自杀式断连**：事件循环被进桌风暴打满 >20s 时，pong 处理排队
   超时，**库主动以 1011 杀掉全部连接**——2026-08-01 21:01 与
   22:52 两次"全体分片同时 1011"的直接机制。✅
   （"20 秒"不是游戏的规定，是 websockets 库的默认值，与官方无关）

**修复方向**：`websockets.connect(..., ping_interval=None)` 关闭
传输层 ping，完全依靠 10s 应用层心跳 + 接收侧静默检测判断连接死活。

## 3. 登录与令牌

- HTTP 登录链（kaptchcate 预注册 → GeeTest v4 点选 → 登录 → UUID），
  全流程见 `captcha-flow.md`、`login-api-capture-20260717.md`。✅
- token 绑定登录 IP：登录/刷新/WS 必须同一出口，否则会话不匹配。✅
- WS 登录帧 jti **单连接消费**：一条 token 只能养活一条 WS；
  新连接建连前必须刷新（venue/launch）拿新 JWT。✅
- venue/launch 返回 `no_params_in_url` = 平台会话冷却期（多发生于
  WS 断开后的短时间内或跨进程接力时），需要退避重试或完整重登。✅

## 4. 设备与浏览器指纹

- **deviceId 三段式**：前两段（fixedDeviceId）按账号持久化
  （官方存 localStorage），第三段每条连接随机。✅
- **UA**：按账号固定（池中绑定），含色深/分辨率/时区/触屏组合
  （hash 选定固定搭配）。✅
- **10115 PROT_DECODE_CONFIG**：登录后服务器推送协议 schema 哈希，
  不一致需热更新并下次上报新哈希（官方 localStorage 持久化）。✅
- **X-API-UUID**：每账号独立生成。✅
- 待验证项：官方 JS 的 WebSocket 子协议/扩展协商、TLS/JA3 指纹、
  断线重连退避曲线（浏览器官方客户端重连节奏未逆向）。⚠️

## 5. 桌台订阅与节奏（平台边界）

- 单桌连续 **5 局未下注 → 102 踢出**（123 帧预警），常规配额，
  靠账号轮换扛。✅
- 掐流主因：**每 IP 桌台订阅总量**（streak ~10 桌/IP 九小时零掐流；
  fullscan 63 桌/IP 2 分钟断崖）。1:1 绑定（≤10 桌/IP）安全工作。✅
- 掐流表现：桌台级静默白名单塌缩（进桌只收 1~2 帧入场爆发后断供，
  大厅路纸照长）。✅
- 进桌风暴（短时大批量 enterTable）→ 约 2 分钟后全体连接被杀，
  重连后会话作废、进桌静默。两次事故均为同一剧本。✅
  （直接机制是本地事件循环饿死心跳，见 §2.2；平台是否另有
  进桌速率监测未排除 ⚠️）

## 6. 断线重连（✅ 2026-08-02 逆向 assets.js 实锤）

> 证据：`HData/.cache/assets.js`（egret 客户端主 bundle，
> v0.0.0.0.2026071417503232，2026-07-14 版；新版本待抓包 diff ⚠️）。

### 6.1 心跳机制（客户端 Socket 类字段直译）

| 字段 | 值 | 含义 |
|---|---|---|
| `_HeartbeatInterval` | 10000ms | 应用层心跳间隔（pid=`PROXY_HEART_BEAT=3`，载荷 `{clientTime}`） |
| `_maxTimeoutTime` | 3 | 连续 3 个心跳周期没收到响应 → 客户端自己 reconnect（`HEART_TIMEOUT=-1008`） |
| `_msgTimeout` | 20000ms | 任何已发消息 20s 无响应 → 触发 reConnection 上报并重连 |
| `_reconnectTimeout` | 10000ms | 重连延时基准 |
| 调度方式 | `setInterval(1s)` | 每秒 tick，距上次心跳 ≥10s 才发 |

**没有任何传输层 WS ping**——浏览器客户端保活完全靠 pid=3 应用心跳，
心跳超时判定窗口约 30~40s（3 个周期），与"服务端 40~60s 无心跳断连"
的实测互为印证。我们关掉 ping、保留 10s pid=3 心跳 = 与官方完全一致。✅

### 6.2 心跳响应检测（checkHeart）

- 每次心跳带 `clientTime`，响应回来算回环耗时，记录网络质量
  （`weakNetLevelN1/N2/N3` 三级弱网提示阈值）；
- 同时校正 `serverTimeDiff`（serverTime - clientTime），波动 >1.5s
  打 warn——**客户端本地倒计时全部用 serverTime+diff 换算**，这也是
  复刻/回放时时间轴对齐的正确做法。

### 6.3 重连流程（reconnect → delayReConnect）

1. 触发：onSocketClose / onSocketError / 心跳超时 / 消息时序错乱
   （`VERSION_ERROR`：乱序消息超过阈值未处理也强制重连！）；
2. 停心跳 → 清空超时消息队列（`sendTimeOutMsg` 上报）→ 关旧连接；
3. `delayReConnect`：setTimeout 延迟（基准 10s）后重连，
   **重连次数 ≥ urls 数量时停止自动重连**，弹"自动重连次数已满，
   是否重连"确认框（人工介入）；
4. **URL 轮换**：`checkAllurl(reconnectCount)` + `CHANGE_URL`——
   客户端持有 `backendDomainUrlList` 多个网关，重连时逐个轮换；
5. 重连成功（CONNECTED）→ `_reconnectCount=0`、`_curTimeoutTime=0`，
   重新登录、重新进桌。

### 6.4 消息时序（复刻关键点）

- 服务器每条下行消息带**递增 version**，客户端 `_serverLastVersion`
  严格按序处理，乱序消息进 `missedMessageQueue` 暂存等补洞；
- 补洞超时（阈值毫秒级）→ 直接 `VERSION_ERROR` 断线重连。
- **回放必须按 version 严格有序喂帧**，否则与真实客户端行为分叉。

## 8. 历史牌局复现（HSys/server 复刻客户端）

### 8.1 可行性结论（2026-08-02）

**可行，且条件比预想的好**。server 现有 FastAPI + Vue + WS 推送骨架，
缺的是一个"回放引擎 + 客户端状态机移植"。关键依据：

- **数据面齐全**：events_raw 已存全量解码帧（按 source_site /
  source_account / table_id / round_id 索引），官方客户端收到的帧
  我们都有；
- **状态机可移植**：assets.js 里的桌台 model 是纯数据逻辑
  （gameStatus 枚举 Nt.BET/OPEN/SHUFFLE、countdownEndTime 用
  serverTime+serverTimeDiff 换算、roadPaper 解析、betPointLimit
  限额计算），不依赖 egret 渲染层，可用 Python/JS 一比一移植；
  路纸解码 hdata 已有现成实现（decode_bead_plate）；
- **时序可控**：客户端靠消息 version 严格定序 + serverTimeDiff
  对齐时钟，回放引擎按 version 排序、按 serverTime 时间轴喂帧
  即可复刻"官方客户端视角"（支持倍速/暂停/单步）。

### 8.2 建议架构

```
server/app/services/replay.py     ← 回放引擎：查 events_raw → 按 version
                                    排序 → 时间轴驱动（1x/10x/暂停/单步）
server/app/services/table_model.py ← 官方桌台状态机移植（Nt/St 枚举、
                                     countdown、roadPaper、限额）
server/app/api/replay.py          ← POST /api/replay {table_id, from, to, speed}
server/app/ws.py                  ← 复用现有 WS 通道推回放状态
web/pages/replay.html             ← 回放页（桌台 UI 骨架 + 路纸 + 局时间轴）
```

两档复刻深度：
- **A 档（数据面复现，推荐先做）**：状态 + 路纸 + 开奖结果 + 倒计时
  与官方客户端完全一致，UI 用 Vue 骨架近似布局。工作量可控。
- **B 档（像素级复刻）**：抽 egret 资源（图集/动画）跑官方渲染层，
  工程量大，只在需要"录屏取证级"还原时才值得。
